# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-board Kanban app: fixed five columns (renameable), drag-and-drop cards, demo sign-in (`user`/`password`, not real auth), and an optional AI co-pilot. Frontend is Next.js (App Router, TypeScript, client-only board) in `frontend/`; backend is FastAPI in `backend/`, persisting to a local JSON file (`backend/data/kanban.json`). The AI co-pilot proxies to Groq (api.groq.com, OpenAI-compatible, free tier) through the backend only — the browser never sees `GROQ_API_KEY`.

There is also `AGENTS.md` at the repo root (symlinked-in via `frontend/CLAUDE.md` → `@AGENTS.md`) with the original business/technical requirements and coding standards — read it for product intent. `frontend/AGENTS.md` is auto-generated by `next dev` (Next.js 16 agent rules banner); don't hand-edit it, and commit it if it reappears in a diff.

## Commands

Backend dependencies are managed with [uv](https://docs.astral.sh/uv/) (`backend/pyproject.toml` + `backend/uv.lock`), not pip/requirements.txt. `uv sync` creates/updates `backend/.venv`; `uv run <cmd>` runs inside it without manual activation.

Backend setup (no Docker):
```bash
cd backend
uv sync
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Backend via Docker Compose (preferred): `./scripts/start.sh` (builds+starts, waits for healthcheck) / `./scripts/stop.sh` (stops+removes). The Dockerfile installs deps via `uv sync --frozen --no-dev` using the official `ghcr.io/astral-sh/uv` image, then runs the app with `uv run`.

Frontend:
```bash
cd frontend
npm install
npm run dev          # http://localhost:3000, proxies /backend-api/* -> backend /api/* (see next.config.ts)
```

Validation — run all of these before considering frontend work done:
```bash
cd frontend
npm run lint
npx tsc --noEmit
npm run test -- --run     # Vitest + Testing Library, tests in frontend/tests/
npm run build
npm run test:e2e          # Playwright, frontend/e2e/ — needs browser binaries; run when relevant
```

Single frontend test file: `npm run test -- --run tests/board.test.tsx`
Single backend test file/case:
```bash
cd backend
uv run pytest -q tests/test_main.py
uv run pytest -q tests/test_main.py::test_name
```
Full backend suite: `uv run pytest -q` (from `backend/`). Add a dependency with `uv add <package>` (or `uv add --group dev <package>` for dev-only); this updates `pyproject.toml` and `uv.lock` together — don't hand-edit the lockfile.

If port 8000 is taken, run uvicorn on another port and set `KANBAN_BACKEND_URL` for the frontend (e.g. `KANBAN_BACKEND_URL=http://127.0.0.1:8001 npm run dev`).

Backend connectivity check (consumes Groq free-tier quota, requires a configured key): `curl http://127.0.0.1:8000/api/ai/check`.

Reset local board data: stop the backend, delete `backend/data/kanban.json`, restart — it reseeds from `SEED_DATA` in `backend/app/repository.py`.

## Environment

Copy `.env.example` to `.env` at the repo root (`chmod 600 .env`) and set `GROQ_API_KEY` there if using the AI co-pilot (free at console.groq.com, no credit card). Never put that key in `frontend/.env.local`, any `NEXT_PUBLIC_` variable, source, tests, or commit history — it must stay backend-only. Related vars: `GROQ_MODEL` (default `openai/gpt-oss-20b`, sent with `reasoning_effort: "low"`), `GROQ_TIMEOUT_MS`, `KANBAN_CORS_ORIGINS`, `KANBAN_DATA_PATH` (override the JSON store path), `KANBAN_BACKEND_URL` (frontend rewrite target).

`docker-compose.yml` passes the root `.env` into the backend container via `env_file` — the container never reads a local `.env` file itself (its filesystem doesn't have one), so if `GROQ_API_KEY` isn't reaching the container, check that `env_file` wiring first, not just whether `.env` exists on the host.

`/api/ai/check` and `/api/ai/chat` have no authentication of their own — the frontend's demo sign-in only gates the UI, not the API. Both endpoints sit behind an in-memory per-IP rate limiter (`enforce_ai_rate_limit` in `backend/app/main.py`, 10 req/min) and every Groq request carries a `max_tokens` cap, both there so a caller who bypasses the frontend sign-in can't burn through Groq's daily free-tier request quota (1,000 req/day at time of writing) on its own.

Note: this project previously used OpenRouter as the AI provider (see git history / `docs/PLAN.md` for that era) before switching to Groq directly for reliability (Groq's free tier runs on dedicated hardware, not a shared/oversubscribed pool) and to avoid OpenRouter account billing complexity.

## Architecture

**Data model / relational integrity (backend/app/repository.py, models.py):** the JSON store is relational — flat `users`, `boards`, `columns`, `cards` collections linked by id, not nested. `KanbanRepository._validate_data` revalidates every relationship (unique ids across all collections, valid foreign keys, contiguous zero-based `position` values within each column, exactly 5 columns) on every read, and re-runs full Pydantic validation (`BoardUpdate`) per board. Writes go through `_write`: dump to a NamedTemporaryFile in the same directory, fsync, then atomic `replace()` — do not write `kanban.json` directly. `save_board` replaces *all* columns/cards for a board on every PUT (delete-then-reinsert), so the frontend always sends the complete board state, not a diff.

**API surface (backend/app/main.py):** `GET/PUT /api/users/{user_id}/board` is the only persistence path; `POST /api/ai/chat` is a structured, validated proxy to Groq — it rejects any assistant response that isn't `{assistant_message, board_update?}` JSON, and separately re-validates `board_update`'s shape (ids present, names non-empty) before handing it back, since it's a different shape than the strict `BoardUpdate` model (partial updates are allowed: the model prompt is told to preserve existing ids and only rename/add/remove/reorder). `GET /api/ai/check` is a cheap live connectivity probe, distinct from `/api/ai/chat`.

**Frontend data flow (frontend/app/page.tsx, lib/api.ts):** `page.tsx` owns board state and is the only place that calls `saveBoard`/`fetchBoard`. `Board` (components/board.tsx) is a controlled component when given `columns`/`onColumnsChange` — every local mutation (drag reorder, add/edit/delete card, rename column, AI-applied update) calls `onColumnsChange(next, previous)`, which `page.tsx` turns into an optimistic update + PUT, rolling back to `previous` and surfacing a retry banner on failure. `lib/types.ts` (`Card`/`Column`, no `position`) is the UI-facing shape; `lib/api.ts`'s `ApiCard`/`ApiColumn` (with `position`) is the wire shape — `toColumns()` converts API→UI (sorts by position, drops it), `saveBoard()`/the AI request body convert UI→API (re-derives position from array order). Keep this boundary in mind when touching either shape: array order is the source of truth on the frontend, explicit `position` fields are the source of truth in the API/store.

**AI co-pilot:** `Board` sends the full current board (in API shape) plus a trimmed history (last 8 messages) to `askBoardAssistant`; a returned `board_update` is applied the same way as any local edit (through `onColumnsChange`), so it flows through the same optimistic-save path in `page.tsx`. Before applying a `board_update`, `Board` snapshots the pre-update columns/name in state; a prompt matching `/\bundo\b/i` reverts to that snapshot locally (no Groq request) instead of being sent to the assistant, since the assistant is never shown prior board states and can't reconstruct one itself. On the backend, `ai_chat` retries once (`max_attempts = 2`) if Groq's response is malformed JSON, or if `assistant_message` claims a change (matches `CLAIMED_CHANGE_PATTERN`) but omits `board_update` — small models occasionally do either.

## Conventions (from AGENTS.md)

- Keep it simple — no over-engineering, no defensive programming for cases that can't happen, no speculative features. This is a deliberately minimal MVP (one board, fixed 5 columns, cards have only title+details, no search/archive/filter).
- No emojis, anywhere, ever.
- Dark, board-first UI; don't add generic hero copy or unrelated navigation. Product identity is "Kanban board".
- Demo sign-in and the local JSON store are explicitly not production-grade — don't add real auth or a database unless asked.
