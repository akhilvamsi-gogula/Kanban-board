# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-user Kanban app: real accounts (sign up, sign in, sign out, forgot/reset password), each with one or more private boards (create, switch, delete via the board switcher) of fixed five columns (renameable), drag-and-drop cards, and an optional AI co-pilot. Frontend is Next.js (App Router, TypeScript, client-only board) in `frontend/`; backend is FastAPI in `backend/`, persisting to Postgres (connection string in `DATABASE_URL`) - locally via the `postgres` service in `docker-compose.yml`, in production via a separate managed Postgres instance (e.g. Neon) so data survives the backend service restarting or redeploying. Passwords are bcrypt-hashed; sessions are server-side, tracked via an httpOnly `kanban_session` cookie. Password reset has no real email provider wired up - `POST /api/auth/forgot-password` returns the reset token directly in its response, and the frontend displays it/the reset link on screen instead of emailing it. The AI co-pilot proxies to Groq (api.groq.com, OpenAI-compatible, free tier) through the backend only - the browser never sees `GROQ_API_KEY`.

There is also `AGENTS.md` at the repo root (symlinked-in via `frontend/CLAUDE.md` → `@AGENTS.md`) with the original business/technical requirements and coding standards - read it for product intent. `frontend/AGENTS.md` is auto-generated by `next dev` (Next.js 16 agent rules banner); don't hand-edit it, and commit it if it reappears in a diff.

## Commands

Backend dependencies are managed with [uv](https://docs.astral.sh/uv/) (`backend/pyproject.toml` + `backend/uv.lock`), not pip/requirements.txt. `uv sync` creates/updates `backend/.venv`; `uv run <cmd>` runs inside it without manual activation.

Backend setup (no Docker) - requires a Postgres instance reachable at `DATABASE_URL` (e.g. `docker compose up -d postgres` from the repo root, which publishes it on `localhost:5432`, or a hosted database like Neon):
```bash
cd backend
uv sync
DATABASE_URL=postgresql://kanban:kanban@localhost:5432/kanban uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Backend via Docker Compose (preferred): `./scripts/start.sh` (builds+starts backend and a `postgres` service, waits for healthchecks) / `./scripts/stop.sh` (stops+removes containers - the `postgres_data` named volume persists across this, so account/board data survives; `docker compose down -v` additionally removes the volume and starts fresh). The Dockerfile installs deps via `uv sync --frozen --no-dev` using the official `ghcr.io/astral-sh/uv` image, then runs the app with `uv run`.

Frontend:
```bash
cd frontend
npm install
npm run dev          # http://localhost:3000, proxies /backend-api/* -> backend /api/* (see next.config.ts)
```

Validation - run all of these before considering frontend work done:
```bash
cd frontend
npm run lint
npx tsc --noEmit
npm run test -- --run     # Vitest + Testing Library, tests in frontend/tests/
npm run build
npm run test:e2e          # Playwright, frontend/e2e/ - needs browser binaries; run when relevant
```

Single frontend test file: `npm run test -- --run tests/board.test.tsx`
Backend tests need a Postgres instance too (`docker compose up -d postgres` from the repo root is enough - both `DATABASE_URL` and `TEST_DATABASE_URL` default to that same local instance if unset, see `backend/tests/test_main.py`). An autouse fixture truncates all tables before each test for isolation, so tests share one database rather than each getting its own file the way SQLite tests used to.
Single backend test file/case:
```bash
cd backend
uv run pytest -q tests/test_main.py
uv run pytest -q tests/test_main.py::test_name
```
Full backend suite: `uv run pytest -q` (from `backend/`). Add a dependency with `uv add <package>` (or `uv add --group dev <package>` for dev-only); this updates `pyproject.toml` and `uv.lock` together - don't hand-edit the lockfile.

If port 8000 is taken, run uvicorn on another port and set `KANBAN_BACKEND_URL` for the frontend (e.g. `KANBAN_BACKEND_URL=http://127.0.0.1:8001 npm run dev`).

Backend connectivity check (consumes Groq free-tier quota, requires a configured key): `curl http://127.0.0.1:8000/api/ai/check`.

Reset all local accounts and board data: stop the backend, drop and recreate the Postgres database it points at (for the docker-compose flow: `docker compose down -v` to remove the `postgres_data` volume, then `docker compose up -d --build --wait`), restart - the schema is recreated empty and each new signup seeds its first board from the same default columns `DEFAULT_COLUMNS` defines in `backend/app/repository.py`; additional boards created later reuse the same defaults.

## Environment

Copy `.env.example` to `.env` at the repo root (`chmod 600 .env`) and set `GROQ_API_KEY` there if using the AI co-pilot (free at console.groq.com, no credit card). Never put that key in `frontend/.env.local`, any `NEXT_PUBLIC_` variable, source, tests, or commit history - it must stay backend-only. Related vars: `GROQ_MODEL` (default `openai/gpt-oss-20b`, sent with `reasoning_effort: "low"`), `GROQ_TIMEOUT_MS`, `KANBAN_CORS_ORIGINS`, `DATABASE_URL` (Postgres connection string the backend persists to - required, no file-path fallback), `KANBAN_BACKEND_URL` (frontend rewrite target).

**Persistent data (Render + Neon):** the deployed backend's `DATABASE_URL` env var (set on Render, not committed anywhere) points at a free Neon Postgres project rather than local disk - Render's free web-service tier has no attached persistent disk and the service's filesystem resets on every redeploy/spin-down, so a database that lives outside the web service's container is what actually survives across those. Neon's free tier has no expiry and auto-wakes on the next query after scaling to zero, matching the backend's own idle-then-cold-start behavior. Local dev/test Postgres runs as the `postgres` service in `docker-compose.yml`, backed by the `postgres_data` named volume so it also survives `docker compose down`/`up` (unlike the old SQLite-in-container setup).

`docker-compose.yml` passes the root `.env` into the backend container via `env_file` - the container never reads a local `.env` file itself (its filesystem doesn't have one), so if `GROQ_API_KEY` isn't reaching the container, check that `env_file` wiring first, not just whether `.env` exists on the host.

`/api/ai/check` and `/api/ai/chat` deliberately have no authentication of their own (unlike `/api/board`, which requires a valid session) - a signed-in session isn't required to call them directly. Both endpoints sit behind an in-memory per-IP rate limiter (`enforce_ai_rate_limit` in `backend/app/main.py`, 10 req/min) and every Groq request carries a `max_tokens` cap, both there so a caller who bypasses the frontend sign-in can't burn through Groq's daily free-tier request quota (1,000 req/day at time of writing) on its own. `/api/auth/*` (except `/api/auth/me` and `/api/auth/logout`, which act on an existing session rather than guessed credentials) sits behind a separate limiter, `enforce_auth_rate_limit` (20 req/min per IP), guarding signup/login/forgot-password/reset-password against brute-force and spam.

Note: this project previously used OpenRouter as the AI provider (see git history / `docs/PLAN.md` for that era) before switching to Groq directly for reliability (Groq's free tier runs on dedicated hardware, not a shared/oversubscribed pool) and to avoid OpenRouter account billing complexity.

## Architecture

**Data model / relational integrity (backend/app/repository.py, models.py):** the store is Postgres (connection string in `DATABASE_URL`) - relational tables `users`, `boards`, `columns`, `cards`, `sessions`, `password_resets` linked by id, mirroring the same shape the old SQLite/JSON stores used. Each account can own multiple boards: `boards.owner_id` is a plain indexed column, not unique, so a user may have several rows in `boards` - every board-scoped repository method (`get_board`, `save_board`, `delete_board`) takes `(user_id, board_id)` and checks `WHERE id = %s AND owner_id = %s`, raising `BoardNotFoundError` (→ HTTP 404) on any mismatch so a board id that exists but isn't yours is indistinguishable from one that doesn't exist. `create_user` still seeds exactly one board per new signup; `create_board`/`delete_board` handle the rest, and `delete_board` refuses to remove a user's last remaining board (`CannotDeleteLastBoardError` → HTTP 409) so every account always has at least one. `boards.row_id` (`BIGSERIAL`) exists purely to preserve insertion order for `list_boards` - Postgres has no implicit rowid the way SQLite did. `columns.id`/`cards.id` are unique only *within a board* (`UNIQUE(board_id, id)`), not globally - don't assume a card/column id is unique across the whole database. `KanbanRepository` re-runs Pydantic validation (`BoardUpdate`/`ColumnModel`/`CardModel`) per board on read/write, scoped to that one board rather than a global scan. Writes go through a `threading.RLock`-guarded single connection per operation - do not connect to the same database from a second, unrelated code path outside the repository. `save_board` replaces *all* columns/cards for a board on every PUT (delete-then-reinsert), so the frontend always sends the complete board state, not a diff. Passwords are bcrypt-hashed (bcrypt truncates input at 72 bytes before hashing - inputs longer than that share a hash prefix, a known bcrypt limitation, not a bug here). Session tokens and password-reset tokens are never stored raw - only a SHA-256 hash of each, in `sessions.token_hash` / `password_resets.token_hash`.

**API surface (backend/app/main.py):** Auth: `POST /api/auth/signup` (creates the user + seeds their private board, sets the session cookie, 409 on duplicate username), `POST /api/auth/login` (401 on any bad credential, doesn't reveal which field was wrong), `POST /api/auth/logout`, `GET /api/auth/me` (401 if no valid session), `POST /api/auth/forgot-password` (always 200; `reset_token` in the response is `null` for an unknown username), `POST /api/auth/reset-password` (400 on invalid/expired/used token; invalidates all of that user's existing sessions on success). Boards: `GET /api/boards` (list the signed-in user's boards as `BoardSummary` - id + name only), `POST /api/boards` (create a new board with default 5 columns), `GET/PUT /api/boards/{board_id}` (read/save one board), `DELETE /api/boards/{board_id}` (204 on success, 409 if it's the user's only board). All five are session-scoped via the `get_current_user` dependency (401 if unauthenticated) and, for the id-parameterized routes, ownership-checked against `board_id` - a board that exists but belongs to someone else returns 404, same as a board id that doesn't exist at all. There's no separate `user_id` anywhere in these URLs; the session determines whose boards are in scope, and `board_id` alone selects which one. `POST /api/ai/chat` is a structured, validated proxy to Groq - it rejects any assistant response that isn't `{assistant_message, board_update?}` JSON, and separately re-validates `board_update`'s shape (ids present, names non-empty) before handing it back, since it's a different shape than the strict `BoardUpdate` model (partial updates are allowed: the model prompt is told to preserve existing ids and only rename/add/remove/reorder); the request's `board` field must carry the id of whichever board is currently active in the frontend, since a chat request always targets exactly one board. `GET /api/ai/check` is a cheap live connectivity probe, distinct from `/api/ai/chat`.

**Frontend data flow (frontend/app/page.tsx, lib/api.ts):** on mount, `page.tsx` calls `getCurrentUser()` (`GET /api/auth/me`) to resolve real signed-in state before rendering the board or the auth flow - there's no client-only "signed in" flag anymore. Once signed in, `page.tsx` calls `listBoards()` (`GET /api/boards`) to populate a `boards`/`activeBoardId` pair of state, defaulting `activeBoardId` to the first board returned (there's no server-side "last active board" concept - this is plain client state, not persisted). A second effect keyed on `activeBoardId` calls `fetchBoard(boardId)` (`GET /api/boards/{board_id}`) whenever the active board changes. `page.tsx` is the only place that calls `fetchBoard`/`saveBoard`/`createBoard`/`deleteBoard` (all now board-id-scoped - `saveBoard(boardId, name, columns)` PUTs `/api/boards/{board_id}`). `persistBoard` guards against a save-in-flight race: it captures the `boardId` being saved and discards the response (success or rollback) if the user has since switched to a different board, so a slow save for a board that's no longer active can't clobber whatever board is now on screen. `Board` (components/board.tsx) is a controlled component when given `columns`/`onColumnsChange` - every local mutation (drag reorder, add/edit/delete card, rename column, AI-applied update) calls `onColumnsChange(next, previous)`, which `page.tsx` turns into an optimistic update + PUT, rolling back to `previous` and surfacing a retry banner on failure. `Board` also renders a `BoardSwitcher` (components/board-switcher.tsx) in the topbar when given `boards`/`activeBoardId`/`onSwitchBoard`/`onCreateBoard`/`onDeleteBoard` props - it lists the user's boards, and offers create/delete (delete is hidden client-side when only one board remains, mirroring the backend's "always keep at least one board" rule). `Board`'s AI co-pilot call passes the active board's real `id`/`owner_id` (via `boardId`/`ownerId` props, both optional with demo-mode defaults) rather than the old hardcoded `"demo-user-board"`/`"demo-user"` stub, since a chat request must target the board actually on screen. `lib/types.ts` (`Card`/`Column`, no `position`; plus `BoardSummary` for the switcher's list view - id + name only) is the UI-facing shape; `lib/api.ts`'s `ApiCard`/`ApiColumn` (with `position`) is the wire shape - `toColumns()` converts API→UI (sorts by position, drops it), `saveBoard()`/the AI request body convert UI→API (re-derives position from array order). Keep this boundary in mind when touching either shape: array order is the source of truth on the frontend, explicit `position` fields are the source of truth in the API/store. `lib/api.ts`'s shared `request()` helper sends `credentials: "include"` on every call so the session cookie flows through the Next.js dev-server rewrite proxy (`/backend-api/*` → backend `/api/*`) - that rewrite is server-side, so from the browser's point of view every request is same-origin and the session cookie just works without CORS gymnastics.

**AI co-pilot:** `Board` sends the full current board (in API shape) plus a trimmed history (last 8 messages) to `askBoardAssistant`; a returned `board_update` is applied the same way as any local edit (through `onColumnsChange`), so it flows through the same optimistic-save path in `page.tsx`. Before applying a `board_update`, `Board` snapshots the pre-update columns/name in state; a prompt matching `/\bundo\b/i` reverts to that snapshot locally (no Groq request) instead of being sent to the assistant, since the assistant is never shown prior board states and can't reconstruct one itself. On the backend, `ai_chat` retries once (`max_attempts = 2`) if Groq's response is malformed JSON, or if `assistant_message` claims a change (matches `CLAIMED_CHANGE_PATTERN`) but omits `board_update` - small models occasionally do either.

## Conventions (from AGENTS.md)

- Keep it simple - no over-engineering, no defensive programming for cases that can't happen, no speculative features. This is a deliberately minimal MVP (fixed 5 columns per board, cards have only title+details, no search/archive/filter).
- No emojis, anywhere, ever.
- Dark, board-first UI; don't add generic hero copy or unrelated navigation. Product identity is "Kanban board".
- Real accounts, hashed passwords, and real sessions exist now (added at explicit user request) - but this is still a local/single-instance app, not a production deployment. Don't add things like real email delivery, OAuth/SSO, or production-hardening (HTTPS enforcement, secret rotation, multi-instance session storage) unless asked; the password-reset flow intentionally surfaces the token in-app instead of emailing it, for the same "keep it simple" reason.
